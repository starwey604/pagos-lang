# M3 前置准备计划

状态：P0/P2 已完成，P1 已采集重构前基线，P3–P6 推进中，2026-09-26。
起点为 M2 核心基线提交 `fb8eb8d`。
本文是进入 M3 前的工作清单，不表示其中的接口或能力已经实现。
完成情况、选型结论和阻项统一更新在本文，不另建逐项验收报告。

## 1. 目标与范围

M2 已证明可解释的部分求值和残留程序正确性；M3 要把它推进到真实裸机程序：
目标平台正确的类型与布局、运行时调用和内存访问，以及可链接、可执行的固件。
先在 QEMU RV32 `virt` 上建立裸机自动验证闭环，再按项目需求扩展架构与实机。
本轮只处理这些能力必然触及的基础接口和验证条件，不提前完成 M3。

进入 M3 前计划完成：

- 建立可重复的 Release 性能测量和编译器自动回归。
- 整理类型、整数常量和聚合值接口，避免按位宽复制整套代码。
- 建立目标配置与布局查询边界，分开宿主信息与目标信息。
- 明确真实调用、运行时效果和缓存之间的接口约束。
- 固定首个模拟平台的配置、工具链和后续实现顺序，不以实机选型为前置条件。

不作为本轮前置条件：总内存限制、全面性能优化、全局 arena 迁移、动态数组、
Runtime 递归、MLIR、JIT、自托管，以及构建能力系统。总内存控制继续延期，
与[已确认的 M2 范围](milestone-2.md)保持一致；测量峰值内存不等于实施限额。

## 3. 工作清单

### P0：模拟平台与工具链确认

- [x] 首验证平台采用 QEMU RV32 `virt`：单核、裸机，不启动 Linux，
  不绑定某颗 CH32、STM32 或厂商 HAL。
- [x] 固定 QEMU 版本、machine、CPU/ISA 扩展、目标 triple、ABI 和启动模式，
  不依赖模拟器默认启用的特性；具体配置在启动冒烟测试中验证。
- [x] 提供最小 C/汇编启动代码与链接脚本，验证入口、栈、数据段初始化和 UART。
  这是环境自检，不表示 Pagos 已实现目标文件输出或 MMIO。
- [x] 核实目标工具链、启动支持与运行库是否匹配；规划 compiler-rt builtins
  或 libgcc 的使用边界，不把宿主运行库当成目标运行库。
- [x] 建立无界面测试入口，检查预期输出、成功/失败状态及超时；若用 semihosting
  辅助退出，应与 UART/MMIO 验证分开，不能仅凭宿主代理输出判定外设访问正确。
- [x] 将启动代码、链接脚本、设备地址和退出协议放在独立平台支持目录，
  编译器核心只接收目标配置，不硬编码 `virt` 的设备映射。

2026-09-26：`python3 scripts/check_rv32.py` 的 Clang/LLD 22.1.8 与
RISC-V GCC 15.2.0 两条链路均通过成功、主动失败、BSS 初始化缺失、data
复制缺失、超时共 10 项检查。QEMU 固定为 11.1.1，RV32IMAC/ILP32，
使用匹配的目标 libgcc，并实际执行 64 位除法。宿主 compiler-rt 不用于目标。
配置与命令见[开发指南](development.md#rv32-environment-probe)。

交付与验收：固定配置、启动支持与可重复的 C/汇编冒烟测试。
[QEMU `virt`](https://www.qemu.org/docs/master/system/riscv/virt.html)
是通用虚拟平台，不是 CH32 模型。先验证编译器与裸机工具链，随后用 Cortex-M
或其他架构检查可移植性；真实 MCU、烧录、时钟与设备差异随项目需求再验证。
指令集选择本身不保证平台无关，目标与板级差异必须保持隔离。

### P1：可重复的性能基线

- [x] 使用 `release` 构建测量编译器，不用 Debug 或 ASan 数据判断优化收益。
- [x] 用现有 Python 基础设施增加测量脚本，覆盖 CRC、重复缓存命中、不同特化
  参数、较大聚合构造和复杂控制流；样例保持可控，不使用可能耗尽宿主的压力值。
- [x] 分别测量 `check`、`emit-mir`、`emit-llvm` 的端到端成本。
  各命令数据包含公共前端成本，不将二者差值宣称为精确的单阶段耗时。
- [x] 固定预热和重复次数，记录中位耗时、波动范围、峰值进程内存、MIR/LLVM
  输出大小，以及已有 fuel/特化/构造统计。
- [x] 保存提交号、构建模式、工具版本、机器信息、输入规模和显式预算参数。
  输出应便于机器比较；临时 IR、完整测量日志不作为源码提交。

交付与验收：提交样例和可复现脚本；记录一组 M2 起点数据，并在重构后以相同
环境和参数复测。不得预先承诺加速比例，不在共享 CI 上设置脆弱的毫秒门槛。
若出现超过重复测量波动的持续退化，先解释或修复，再接受改造。

编译器运行速度与生成代码的运行速度分开记录。M3 模拟阶段可比较同目标、同优化
条件下的 C 行为与 ELF 段大小；不能将 QEMU 耗时当成实际 MCU 周期、时序或功耗。
实机 flash/RAM 和周期测量留到硬件阶段，不能由宿主编译耗时推断。

测量入口：`python3 scripts/benchmark.py --output build/benchmarks/baseline.json`。
重构前编译器仍为 M2 实现，Clang 22.1.8 Release，2 次预热、7 次重复；
本机初测如下（毫秒，含进程启动成本，不是性能承诺）：

| 样例 | check 中位数 | emit-llvm 中位数 | LLVM 字节数 |
| --- | --- | --- | --- |
| CRC | 13.81 | 14.52 | 12202 |
| 4096 元素 / 4088 缓存命中 | 10.71 | 11.55 | 31682 |
| 1024 个特化 | 10.30 | 11.06 | 12811 |
| 8192 元素聚合 | 15.93 | 17.13 | 96260 |
| 嵌套 Runtime 循环 | 9.23 | 9.88 | 1168 |

原始结果保留在本机 `build/benchmarks/m2-before.json`，含范围、RSS 和版本。
聚合 check 的范围为 10.88–16.78 ms，说明单轮噪声不可忽略；重构后须重复
比较，不能直接按表中差值宣称优化。暂未据此引入聚合共享或新分配器。

### P2：编译器自动回归

- [x] 在现有文档 CI 之外增加编译器构建和测试，覆盖 Clang debug、GCC debug
  和 ASan/UBSan；增加 Release 构建与运行冒烟检查，按成本分层调度。
- [x] 固定可复现的依赖安装方式或构建镜像，记录 LLVM 22、C++26 编译器、
  CMake、GoogleTest、lit/FileCheck 的实际版本，不依赖 runner 默认工具链。
- [x] 保留既有测试的语义覆盖，包括诊断、必要的 HIR/MIR/LLVM 结构、运行顺序、
  陷阱和 CRC 差分测试；不冻结所有内部文本输出。
- [x] 在自动检查中覆盖格式、clang-tidy、文档链接和补丁空白问题，保存失败日志。
- [x] 验证从干净构建目录可复现，不依赖开发机已有的编译产物。

实施结果：`ci/Dockerfile` 固定 amd64 镜像摘要及 2026-09-25 Arch 归档，
`scripts/ci.py` 是本地/工作流共用入口。断网容器内四种配置均从全新目录
构建并通过 50 单元 + 202 lit 及三个基准源程序检查；本机 debug 质量检查
与 RV32 检查通过。日志和实际版本保留于 `build/ci-logs/`。
GitHub 工作流已经写入，但未推送、未在远端运行；不将本地结果冒充远端结果。

交付与验收：工作流和依赖配置进入仓库，具备执行环境时实际跑通。
本地通过不等于远端 CI 通过；若发布或远端执行需要权限，明确记录阻项，
不自动推送、配置远端 runner 或改变仓库权限。
当前基线为 50 个单元测试、202 个 lit 测试，多数 lit 用例验证语言或 CLI 的可见
行为。数量不是目标：允许合并重复用例、迁移测试框架或重写实现相关断言，
但必须保留仍有效的行为覆盖；不能通过删除失败用例掩盖退化。

测试的长期维护原则：

- 长期保留语言行为与历史 bug 的最小复现，例如两阶段算术一致性、缓存不丢效果、
  越界检查、提前返回和 CRC 结果。文件组织或测试入口可变，覆盖目的不随重构消失。
- AST/HIR/MIR 的 C++ 单元测试随内部接口迁移；即使以后重写编译器，这部分也可能
  重写，但源程序及预期行为通常可以复用。记录内部假设，不把它们误当语言规则。
- IR 快照只断言有意义的结构、类型和必要操作，不锁死无关编号、临时变量名或
  指令排版。诊断快照继续遵守现有呈现契约，措辞变化需有意审阅。
- 如果语言规则有意改变，在同一变更中更新规范和测试；新增能力使旧的“不支持”
  用例过时时，将其改为相应正例，而不是要求永远拒绝这类程序。
- CI 是运行测试的调度机制，不是固定不变的产品接口。PR 优先执行主要构建、
  快速回归与文档/格式检查；其他编译器、sanitizer 和较慢测试按主线、定期或
  风险触发执行。准备基线及关键重构仍运行完整矩阵，不把每个组合都强制放到
  每次小改动的路径上。性能测量暂不设置噪声敏感的硬门槛。

### P3：类型、常量和依赖边界

- [ ] 将整数位宽/符号、数组元素类型/长度、记录身份和字段描述整理为可组合表示，
  避免每增加一种整数就再增加一个专用数组类型枚举。
- [ ] 明确区分语法类型标注、语义类型和具体 MIR 类型。语法节点不保存推断结果；
  未确定长度、错误类型等语义状态不能泄漏为合法的残留类型。
- [ ] 建立统一整数值接口；验证 LLVM `APInt` 作为实现底座的可行性。
  用现有 `u32` 的回绕、移位、除零规则做对照，不改变语言语义。
- [ ] 集中常量的相等、哈希、打印和转换规则，保持记录的名义身份以及类型信息。
  统一规则不等于强行把所有阶段的类型合并为一种类型。
- [ ] 明确聚合值的共享与复制路径，检查缓存键和 Sequence 常量复制。
  只有 P1 数据支持时才实施局部共享/复制优化；常量池和全局分配器改造不是门槛。
- [ ] 将明显重复的整数检查和聚合处理收敛到小型内部接口，按职责拆分过大的函数，
  不为消除几个 switch 就引入通用元编程或 IR 框架。

交付与验收：全部 M2 源程序、阶段解释、求值顺序、预算与缓存规则保持一致；
任何有意的输出变化必须单独说明并补测试。以库级测试证明表示可支持多位宽，
但完整的新整数语法、转换规则及 `usize` 源程序支持仍属于 M3。

### P4：目标配置与布局查询

- [ ] 建立 Pagos 自有的 `TargetConfig` 和布局查询接口，包含目标 triple、CPU、
  features 等信息，由后端适配 LLVM `TargetMachine` / `DataLayout`。
- [ ] 在编译会话中显式传递目标信息；禁止从宿主 `sizeof` 推断目标指针宽度、
  对齐或记录布局。布局查询与语言类型规则分离。
- [ ] 明确默认宿主配置与显式目标配置的行为；为不支持的目标提供可解释错误。
- [ ] 验证不同指针宽度目标的查询，以及同进程切换目标时没有布局缓存串用。
  若缓存跨会话复用，目标相关信息必须参与其身份判定。
- [ ] 检查 CMake 的 LLVM 组件依赖，不能只因本机使用单体 LLVM 库就漏掉
  组件链接配置；验证所需目标后端确实可用。

交付与验收：库级查询和宿主回归通过，必要的 LLVM 模块目标布局与配置一致。
本切片不实现目标文件输出、固件链接 CLI 或 C ABI 聚合传参。
数据布局查询结果本身也不能被当作完整 C ABI 规则。

### P5：调用、效果与缓存接口准备

- [ ] 检查并收敛既有“是否有残留工作”和“是否可缓存结果”的判断入口。
  Static 值可以伴随 Runtime 效果，不能只看结果阶段就判断纯度。
- [ ] 保留缓存命中时的参数求值、未使用读取、陷阱和提前返回等回归。
- [ ] 明确未来通用 MIR 函数/调用所需的参数、结果、符号身份和调用约定信息，
  为摆脱单个 `pagos_main` 的简化表示确定迁移位置，不预建大量未使用节点。
- [ ] 约定普通外部调用默认不能编译期执行；volatile/MMIO 必须保留其访问，
  不能因地址为 Static 就折叠、删除或缓存读取结果。
- [ ] 明确目标地址/符号引用与宿主指针的区分；目标地址不在编译器进程中解引用。
  未来指针权限、别名和 unsafe 规则由 M3 单独实现。

交付与验收：既有行为的内部判断接口与回归齐全；未来调用/效果约定在本文或现有
架构文档中明确标注为设计，不误报为已实现。通用残留调用、extern、volatile、
指针语法及跨语言执行测试留到 M3。

## 4. 外部依赖决策

源码依赖采用 FetchContent，不引入 Git submodule；固定完整 commit 或归档
SHA-256，提供本地源码覆盖与离线入口，显式区分系统包和固定源码模式。
工具链继续独立安装，宿主库与目标运行库分开构建。完整约定见
[开发指南](development.md#dependency-policy)，不为尚未选用的库预建下载逻辑。

| 领域 | 前置计划中的处理 |
| --- | --- |
| 位宽整数 | 优先验证 LLVM `APInt`；完成边界和成本评估后记录采用结论 |
| 目标布局与代码生成 | 继续复用 LLVM 22，不在准备期升级到其他主版本 |
| 链接与目标文件工具 | 复用外部 LLD/交叉工具链，不嵌入自制链接器 |
| 测量 | 先用 Python 脚本；确有微基准需求时再考虑专用库 |
| 容器与分配器 | 不全面替换 STL；只对测量确认的热点做局部选型 |
| 类型、阶段、效果和诊断 | 保留 Pagos 自有语义，不交给外部框架定义 |

若采用 `APInt`，必须同时更新当前“前端不使用 LLVM API”的架构约束：
仅允许数值实现层私有复用 LLVM Support/ADT；语法、语义接口不能直接携带
`llvm::Type` 或 `llvm::Value`，也不以宿主表示定义目标语义。
不要为了包装一个标量而额外引入每值一次的堆分配。该选型评估不能跳过
Static/Runtime 算术一致性，也不能绕过既有 checked 操作的诊断。

复用方向的参考为 [APInt](https://llvm.org/docs/doxygen/classllvm_1_1APInt.html)、
[LLVM 目标输出](https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/LangImpl08.html)
和 [Clang 工具链组成](https://clang.llvm.org/docs/Toolchain.html)。
接口细节以仓库固定的 LLVM 22 头文件和实际测试为准，不照搬主干 API。

## 5. 进入 M3 的检查点

- [ ] P1 的测量可复现，性能结论明确区分事实、波动和未验证假设。
- [ ] P2 的自动回归可用，未把仅本机成功标成远端验证完成。
- [ ] P3/P4 已形成可扩展的内部边界，M2 行为没有未解释的退化。
- [ ] P5 的运行时效果与缓存约束明确，没有通过提前实现整套 M3 来扩大准备期。
- [ ] QEMU RV32 `virt` 配置与最小启动测试已确认；缺失工具或权限有明确说明。
  不要求购买硬件、选择具体 MCU 或完成烧录。
- [ ] Clang、GCC、ASan/UBSan 回归及 Release 冒烟、格式、静态和文档检查通过。
- [ ] 汇总实际完成项与延期项，形成独立准备基线提交，不自动推送远端。

若某项仍缺外部条件，应明确缩小为“宿主准备基线”，由项目负责人确认后再推进，
不能静默跳过检查点。没有必要设置固定性能提升比例，也不等待全部 M2 性能债清零。

## 6. M3 内部的后续顺序

准备完成后按垂直切片推进，不把下列实现作为 P0–P6 的验收要求：

1. 多位宽整数与 `usize`：确定转换、溢出和移位规则，保持两阶段行为一致。
2. 通用残留函数、目标文件输出与最小 C 互操作：先支持约定的标量/指针 ABI
   子集，用 C 对照测试验证；指针在此仅作受限边界值，完整访问语义随后补齐。
3. 指针访问、受控 unsafe、记录/枚举布局、全局变量和段，以及 volatile/MMIO。

   错误路径，必要时补定时器/中断测试；使用输出和状态判据，不要求物理 LED。
5. 与同目标、同优化条件的 C 程序比较行为与 ELF 段大小，形成模拟平台基线。
6. 根据覆盖缺口加入 Cortex-M 等第二架构；实机目标随需求确定，再验证 blink、
   UART、真实启动/外设差异和硬件性能。模拟平台基线与实机验证分别记录状态。
